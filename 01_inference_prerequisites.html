공유 추론 vs 전용 배포의 손익분기점

모델: Cost = min(Tokens × Rate, GPU_Hours × Wage)장부로 보면: 건당 택배비 vs 월세 화물트럭

장부로 보면 (Cost Tradeoff)

창업 초기 주문량이 적을 때는 배송 건당 3,000원씩 외주 택배를 쓰는 게 이득입니다. 하지만 하루 배송량이 수만 건으로 늘어나면 월세 트럭을 계약하고 기사를 고용하는 전용 배차가 훨씬 저렴해집니다.

신경망 인프라에서는

초기엔 토큰당 과금되는 퍼블릭 API(Shared Endpoint)가 엔지니어링 오버헤드 0으로 안전합니다. 그러나 트래픽이 커지면 GPU 인스턴스를 직접 대여해 올리는 전용 서빙이 토큰당 단가를 1/5 이하로 낮춥니다.

배포 방식 결정 컷: 토큰당 과금 API vs 시간당 전용 GPU의 단위 경제학 갈림길

일일 토큰량: 15M 토큰/일
전용 GPU 구성: A10G × 2대 ($2.5/hr)
현재 트래픽에선 전용 배포가 공유 API 대비 매월 약 $420 절감됩니다. 손익분기점을 돌파했습니다!

초보자를 위한 장부 계산법

  1. 공유 추론의 장점: 콜드 스타트 없음, 사용한 만큼만 지불, 초기 엔지니어링 리소스 절약.
  2. 공유 추론의 한계: 사용량과 비용이 1:1 선형으로 폭증하며, 이웃 노이즈(Noisy Neighbors)로 인해 지연시간 보장이 불가능함.
  3. 전용 전환 3대 이유: 규모(Scale), 특화 모델 운영(Specialization), 복합 모델 파이프라인(Orchestration).
현장에 옮기면 단순 프로토타입 단계에서 무리하게 자체 vLLM 클러스터를 구축하면 유휴 GPU 비용으로 월 수백만 원이 낭비됩니다. PMF(제품-시장 적합성) 달성 전에는 상용 API로 기동성을 확보하세요. 비유의 한계: 전용 GPU는 서버 다운타임과 배포 유지보수 인건비가 추가로 발생합니다.

도메인 특화: 파인튜닝과 지능 증류

전략: 671B 범용 ➔ 3B 맞춤형 경량화장부로 보면: 만능 박사 대신 전속 통역관

장부로 보면

모든 언어와 인문학, 코딩을 다 아는 고연봉 수석 석학에게 사내 SQL 쿼리 작성만 시키는 것은 심각한 인건비 누수입니다. 기본 어학력만 갖춘 주니어에게 사내 DB 스키마만 집중 훈련시키는 편이 압도적으로 빠르고 쌉니다.

신경망 인프라에서는

수천억 파라미터의 프론티어 모델은 추론 비용과 메모리 대역폭을 과도하게 소모합니다. Text-to-SQL처럼 닫힌 도메인에서는 3B 소형 모델을 파인튜닝하거나 대형 교사 모델에서 증류(Distillation)하여 대등한 정확도를 얻습니다.

테스트 데이터: 실제 비즈니스 질의 500건
테스트 완료: 3B Fine-tuned 모델이 671B 프론티어 모델 대비 정확도 97.4% 수준을 유지하면서 추론 비용은 92% 절감했습니다!

파인튜닝 vs 지능 증류(Distillation)의 핵심 차이

  1. 파인튜닝: 모델의 아키텍처와 가중치 수는 유지한 채, 도메인 데이터셋으로 특정 도메인의 정답 가중치로 갱신함.
  2. 증류(Distillation): 대형 교사(Teacher) 모델의 내부 확률 분포(Logits) 자체를 작은 학생(Student) 모델에게 가르쳐 행동 양식을 전수함.
  3. 굿하트의 법칙(Goodhart's Law): MMLU 같은 범용 벤치마크 점수에 매몰되지 말고, 서비스 실제 태스크 기반의 자체 Evals를 구축해야 함.
생성 AI로 치면 DeepSeek-R1(671B) 출시 직후 Llama-3 8B 기반으로 증류된 오픈 모델들이 오픈소스 생태계에서 폭발적 인기를 얻은 이유와 같습니다. 작아서 단일 GPU에서도 날아다니기 때문입니다. 비유의 한계: 증류된 모델은 교사 모델이 가진 편향과 오답 생성 패턴까지 그대로 흡수할 위험이 있습니다.

지연시간 vs 처리량, 그리고 꼬리 지연(P99)

지표: TTFT, TPS, P50, P99장부로 보면: 급행 개인 창구 vs 심야 대량 결제 배치

장부로 보면

은행 창구에서 한 명의 VIP 고객을 위해 직원이 즉시 응답하는 '지연시간 최적화'와, 야간에 전산실에서 수백만 건의 이체 내역을 묶어서 한 번에 청산하는 '처리량 최적화'는 설계 철학이 완전히 다릅니다.

신경망 인프라에서는

챗봇은 첫 토큰이 뜨는 시간(TTFT)과 초당 토큰(TPS)이 생명입니다. 반면 팟캐스트 전사나 문서 임베딩 같은 오프라인 작업은 개별 지연을 희생하고 배치 크기를 극대화해 GPU당 처리량을 최대화합니다.

동시 접속자 수: 16명
서빙 모드:
지연시간 지표 분석: Median(P50)은 180ms로 쾌적하지만, 큐잉 적체로 인해 P99 꼬리 지연은 1,240ms까지 치솟았습니다. 100명 중 1명은 서비스 먹통을 의심합니다!

꼬리 지연(Right-skewed Distribution)을 봐야 하는 이유

  1. 평균의 함정: LLM 응답 시간은 정규분포가 아니라 오른쪽으로 긴 꼬리를 갖습니다. 평균값만 보면 이상치(Outlier)의 고통이 가려집니다.
  2. P90 / P99 관리: 10번 중 1번, 100번 중 1번 발생하는 병목 지연이 유저 신뢰를 무너뜨립니다.
  3. TTFT vs TPS 분리: TTFT는 프롬프트를 한 번에 읽는 컴퓨팅 바운드(Prefill), TPS는 가중치를 메모리에서 계속 읽어오는 메모리 대역폭 바운드(Decode)입니다.
조수

장부를 확인하니 배치 크기를 1에서 32로 올리면 총 토큰 생산량은 4.2배 늘지만, 개인 체감 지연은 3배 느려져요. 용도별로 서버를 쪼개야 해요!
